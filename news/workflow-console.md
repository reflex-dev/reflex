`reflex workflows console` serves the operator console: a Reflex app over the workflow store with four pages — runs (filterable by workflow and status), one run's story (state, steps and attempts, result or error, children, and the full history with who did what and why), the worker fleet with per-release active counts, and channel deliveries with dead-letter replay. Cancel, retry, skip, and resume are the same kernel operations the CLI uses; each carries the operator's name (`REFLEX_ACTOR`, else the login user) and a reason, and lands in the run's own history. The console never executes steps — its runtime opens the store without claiming anything — and it binds loopback by default, since it has no login of its own; exposing it is a deliberate choice behind an authenticating proxy. The command materializes the minimal Reflex project the app needs and hands off to `reflex run`.

The console signs operators in with the service's own scoped API tokens: `read` to view, `operate` to repair. Tokens bound to a principal via `REFLEX_WORKFLOW_API_TOKEN_PRINCIPALS` (`alek=tok1;deploy-bot=tok2`) sign actions as that name — on the console and on the HTTP API alike, where the credential now outranks the `X-Actor` header — and an unbound token records the name the operator typed. With no token configured the console stays open, which is the loopback default.

Pages stay live: each re-reads the store every few seconds while it is mounted and stops when the browser leaves it. Polling the store rather than streaming from a worker is deliberate — it is what survives a worker restart.
