SUMMARY: The Redis lock/lease rewrite (#7534) holds up under real load. Across 4 installs (pip-stock redis-py 8.1.0, shared `new` with 8.2.0b1, redis-py 7.4.1, and 0.10.1), GRANIAN_WORKERS 1/2/4 and oplock on/off, every final count was exact and uncontended latency did not regress. Oplock contention stalls dropped from 5-10 s on 0.10.1 to about 1 s, and lost release notifications now cost 0.33 s instead of 8.35 s. #7412/#7696 (raise mid-yield, supersedes), #7616 (hot reload, disk and Redis) and #7590 (spawn and strict hot reload setters) are verified fixed in Chromium against a failing 0.10.1 baseline. Python 3.11 shutdown with events in flight never hung (16 runs). New findings are not regressions: a Redis outage longer than about 5 s permanently drops cross-worker updates to existing clients, and a kill -9 of one worker stops the whole server and resets the session. One opt-in oplock path still leaves a 1 s stall.

ISSUES:
- TITLE: After a Redis outage longer than ~5 s, cross-worker updates to already-connected clients are silently dropped until a new socket connects to that worker
  SEVERITY: medium
  REGRESSION: no
  REPRO: Copy `bin/` to $SB/apps/redis_runtime/bin and `apps/lockapp` to $SB/apps/redis_runtime/src/lockapp, then run `bash $SB/apps/redis_runtime/bin/faults.sh redis_runtime-stock 0 2 out.jsonl redis_restart`. This is prod with GRANIAN_WORKERS=2 and redis on 8237. It connects one socket client, runs SHUTDOWN SAVE, keeps redis down 10 s, restarts it on the same dump, then sends 10 POST /api/bump (app.modify_state) on fresh connections. Read `cross_worker_after_restart` in out.jsonl.
  EVIDENCE: api_deltas_received = 10 - bumps_other_worker in all runs (stock 6/10 with 4 on the other worker, r7 5/10 with 5, 0.10.1 9/10 with 1). Server log: `_subscribe_lost_and_found_updates: task exceeded exception limit 5 within 60.0s` and the same for `_subscribe_socket_record_updates` (logs/redis_restart-*-server-excerpt.txt). The tasks are re-created only in on_connect/link_token_to_sid, so a tab that stays connected never again receives bg/out-of-band updates produced on another worker.
- TITLE: kill -9 (e.g. OOM) of one granian worker stops the entire prod server; on restart the returning client is given a new token and loses its session
  SEVERITY: medium
  REGRESSION: no
  REPRO: `bash $SB/apps/redis_runtime/bin/kill9.sh redis_runtime-stock 2 out.jsonl`. This is prod + Redis with 2 workers. It connects one socket client, sends slow(5000), and kill -9s that client's worker 0.5 s later. The server then exits; the script restarts it and reconnects with the same token. `kill9.sh prev 2 out.jsonl` gives the same result.
  EVIDENCE: logs/kill9-stock-server-tail.txt shows `[ERROR] Unexpected exit from worker-1` then `Info: Reflex app stopped.` In logs/kill9.jsonl the resume run gets `new_token` on connect and count restarts at 1. The dead worker's `token_manager_socket_record_<token>` key triggers duplicate-tab detection.
- TITLE: REFLEX_OPLOCK_ENABLED with >=2 workers: a second waiter on the same instance is passed over by the next lease and stalls ~1 s (lock_expiration/10)
  SEVERITY: low
  REGRESSION: no
  REPRO: Start `apps/lockapp` in prod with REFLEX_OPLOCK_ENABLED=true GRANIAN_WORKERS=2 and Redis. Run `$SB/envs/redis_runtime-drv/bin/python bin/load.py http://localhost:<P> --clients 1 --events 300 --mode pipe --api 100 --api-conc 2` 6 times, then again with `--api-conc 1`.
  EVIDENCE: logs/conc_new_op1_w2.jsonl: with conc 1, 0/6 runs have a wait over 500 ms; with conc 2, 3/6; with conc 4, 4/6; each stall is 1010-1040 ms. In the debug log (logs/dbg-op1-smr-excerpt.txt) a new lease is "obtained" while a remote waiter is still queued, and nothing happens until that waiter's 1 s "wait timeout" re-registers it ("OPLOCK CONTEND"). Cause: contenders are a SET of instance ids, and every waiter's `_request_lock_release` exit does `SREM <lock>_waiters <instance_id>`, which deregisters the instance's other queued waiters too. This contradicts part of the #7534 changelog sentence ("events waiting on other instances are no longer passed over by the next lease"). 0.10.1 stalls 5-10 s on the same load.
